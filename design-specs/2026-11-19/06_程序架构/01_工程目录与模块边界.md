# 工程目录与模块边界

本文件是可实施的技术方案。设计规则以[统一规则](../00_统一规则_先读.md)为准。文中的接口签名、目录和 JSON 是编码约定示例；本包尚未提供可运行游戏、服务器或 Unity 工程。

## 技术选型与部署单位

客户端选择项目启动时仍受支持的 Unity LTS、C#、URP 和 Input System。立项时锁定 Unity 补丁号、包版本、Android SDK 和图形 API，记录到工程版本文件。避免在制作到一半时追逐引擎大版本。地图以方格逻辑和3D外观资源组合，同一格可以有地表、机关和多个表现挂点。

战斗规则放在独立纯 C# 程序集，目标选 Unity 与服务端共同支持的 .NET API 子集。该程序集不能引用 UnityEngine、UnityEditor、网络框架、系统时间或文件系统。对战服务使用受支持的 .NET 服务端版本，在 Linux 容器运行同一个规则程序集。主服只负责账号、库存、匹配和结算；房间进程处理一场对战中的命令顺序。原型可让两者运行在同一服务进程，保留接口，在线人数达到需要时再拆部署。

建议持久存储先用 PostgreSQL，一个数据库容纳账号档案、内容版本、结算账本与对局索引。回放事件与压缩快照先存本地开发对象目录，正式环境迁到对象存储。Redis 仅在需要跨进程匹配队列和短期房间定位时加入；首个可玩切片可以直接用内存队列。

## 依赖方向

```text
Unity UI / 3D Presentation ──> Integration ──> Battle API
                                             │
Server Room ─────────────────────────────────┤
                                             v
                                 Battle + Pathfinding
                                      │       │
                                      v       v
                                    Domain <──Content DTO
Server Accounts ──> Persistence
Editor/Compiler ──> Content DTO + Validator + Domain
```

Battle 依赖只读内容索引与状态，Presentation 订阅结果事件。动画结束事件只控制播放队列，不驱动扣血、发牌、冷却或胜负。人物脚步还在播放时，逻辑状态已经由确认命令产生；界面需要以已提交状态决定下一条合法命令。

## 模块职责与公开接口

| 模块 | 输入与输出 | 必须避免的职责混入 |
|---|---|---|
| ContentCatalog | 内容版本号→不可变ID索引 | 不保存玩家装备穿戴状态；不在一局中热更新 |
| LoadoutValidator | 种族、职业、训练点、装备ID、技能ID→合法配置或逐条错误 | 不按玩家自取配装名猜测流派；不添加套装隐性奖励 |
| BattleEngine | BattleState+Command→CommandResult、Events、下一状态 | 不读取角色模型骨骼、音效时长或网络延迟 |
| BoardQueries | 格图、占据、起终点、移动规则→路径/视线/命中格 | 不用 Physics.Raycast 判定逻辑射程或铜路 |
| RuleEvaluator | 一条已编译效果、上下文、预算计数→合法效果请求 | 不执行任意策划脚本，不递归调用另一技能 |
| TurnScheduler | 模式、队伍、轮次→下一激活者、时限、复归入口 | 不给较快客户端额外先手 |
| ObjectiveController | 行动结果→关卡进展、回合/程结束、胜负 | 不从UI是否播放完领奖来决定结果 |
| RoomService | 已认证玩家命令→权威响应、广播、重连快照 | 不接受客户端提交的伤害、装备修正值或胜利结果 |
| RewardLedger | AccountId+RunId+RewardId→幂等到账结果 | 不因重发结算或重连生成第二份奖励 |
| PresentationDirector | 事件+表现配置→动画、VFX、音效、镜头提示 | 不修改战斗数值；可跳过后恢复相同逻辑位置 |

可使用以下接口形状指导编码。具体序列化框架、不可变集合实现由原型技术验证后锁定。

```csharp
public interface IBattleEngine
{
    PreviewResult Preview(BattleState state, BattleCommand command);
    CommandResult Submit(BattleState state, BattleCommand command);
}

public interface IContentCatalog
{
    ContentVersion Version { get; }
    SkillDefinition GetSkill(SkillId id);
    EquipmentDefinition GetEquipment(EquipmentId id);
    MapDefinition GetMap(MapId id);
}
```

`PreviewResult` 和 `CommandResult` 都带输入状态版本。Submit 必须重新校验当时状态，并不能因为客户端曾收到合法预览就跳过费用和目标检查。核心采取“输入状态不可变、创建下一状态”的方式最便于回放；若后续为性能改用原地工作缓冲，提交前仍需保证失败不会留下半次扣费。

## 数据与3D对象绑定

每个战斗单位有稳定 `UnitId`、一个锚格、一个占格形状、一个逻辑朝向。Unity 角色对象通过 `UnitViewBinding` 持有该 ID，不能用场景对象实例号当作回放标识。坐骑与骑手可共用一枚棋子的多个模型挂点，不天然多占一格。巨化时更换占格形状和模型比例，命中去重依旧按 UnitId。

格子高程是规则数据，3D模型高度是表现数据。能站哪层、能否被矮墙掩护、能否跨低障，以格子规则与技能卡为准。3D楼梯、屋顶和桥模型需对齐可行走层；多层地形应显式声明“层ID+格坐标”的入口连接，首版地图只启用单个战斗逻辑层，地下关切换为独立地图。

## 运行规模与上线边界

单场竞技只有4枚英雄棋，首版性能重点在特效叠层、透明毛发和界面刷新。战役允许更多敌人，但建议每个遭遇总活动实体先控制在12枚单位、24件可交互地物以内。这个数量是原型性能预算，超过时应先分析快照、寻路与特效开销，不能凭预算自动删除关卡所需敌人。

本包300件装备属于同一首发设计库。游戏逐章开放研究池，内容工具一次编译完整集合。开发切片可以只激活小部分白名单作验证，余下条目仍保留ID，进入正式版本前逐件通过数值和效果校验。
